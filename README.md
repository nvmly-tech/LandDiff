# LandDiff

По расписанию открывает лендинги в браузере, сравнивает их с эталоном и, если что-то поменялось, присылает в почту и в Telegram скриншот «до», скриншот «после» и подсветку того, что именно изменилось.

Лендингов может быть сколько угодно, добавляются они руками в `landings.yaml`.

Период задаётся `CRON_SCHEDULE` в `.env`. Сейчас там `*/5 * * * *` — каждые пять минут, для обкатки; штатный режим — `0 * * * *`, раз в час. Изменение расписания требует перезапуска службы, в отличие от `landings.yaml`, который перечитывается на каждом прогоне.

## Что считается изменением

Сравнивается не картинка, а содержимое. Со страницы снимается нормализованный список видимых текстов, картинок, ссылок и фонов; изменение хотя бы одного значения — повод для уведомления. Скриншоты и пиксельный дифф нужны только чтобы показать результат.

Так сделано из-за шума. Лендинги полны каруселей, счётчиков онлайна, анимаций и ленивой загрузки: сравнение снимков попиксельно срабатывало бы почти каждый час. Поверх этого работают ещё три фильтра:

- **`ignoreSelectors`** — узлы, которые скрываются перед снимком: баннеры кук, чаты поддержки, тикеры.
- **`ignorePatterns`** — куски текста, вырезаемые перед сравнением: время, счётчики, токены.
- **Подтверждение** — найдя изменение, служба через 20 секунд переснимает страницу. Разошлись снимки — значит это динамика, и уведомление не уходит. Совпали — изменение настоящее.

Отдельно обрабатывается перестановка блоков: если вставить секцию в начало страницы, у всех остальных узлов сдвигаются пути в разметке. Значения, которые «исчезли» в одном месте и «появились» в другом, сводятся между собой и в отчёт не попадают — иначе один вставленный блок выглядел бы как переписанная целиком страница.

## Что приходит в уведомлении

| Картинка | Что на ней |
|---|---|
| `focus_N.png` | Фрагмент «БЫЛО \| СТАЛО» рядом, вокруг каждого скопления правок. Рамки пронумерованы теми же номерами, что и строки в списке изменений. |
| `after_marked.png` | Вся страница целиком с отметками. |
| `before_marked.png` | Эталон с отметками — красным то, что удалили. |
| `pixeldiff.png` | Попиксельная разница. Прикладывается только если вёрстка не поехала: удаление одной строки сдвигает вниз всё под ней, и тогда картинка краснеет целиком без всякой пользы. На диске остаётся всегда. |

Цвета рамок: зелёный — добавлено, янтарный — изменено, красный — удалено.

## Запуск

```sh
npm install
npx playwright install chromium      # локально; в Docker браузер уже в образе

cp .env.example .env                 # заполнить SMTP и токен бота
cp landings.example.yaml landings.yaml

npm run test-mail                    # проверить почту
npm run test-telegram                # проверить бота
npm run baseline -- --all            # снять эталоны
npm start                            # постоянный режим с расписанием
```

В Docker:

```sh
docker compose up -d
docker compose logs -f
```

Данные лежат в `./data` и переживают пересборку контейнера. `landings.yaml` перечитывается на каждом прогоне — чтобы добавить лендинг, перезапускать контейнер не нужно.

## Команды

| Команда | Что делает |
|---|---|
| `npm run list` | Показать лендинги, их `slug` и каталоги |
| `npm run check` | Проверить всё прямо сейчас |
| `npm run check -- --only=slug` | Проверить один лендинг (через запятую можно несколько) |
| `npm run check -- --no-notify` | Проверить, ничего не отправляя |
| `npm run baseline -- --all` | Переснять эталоны — после планового редизайна |
| `npm run test-mail`, `npm run test-telegram` | Проверка связи |
| `npm test` | Юнит-тесты |
| `npm start` | Постоянный режим |

`--only` включает лендинг, даже если у него стоит `enabled: false`.

## Настройка лендинга

Все поля — в `landings.example.yaml`. Из `defaults` значения подставляются в каждый лендинг; `ignoreSelectors` и `ignorePatterns` складываются со списками самого лендинга, остальные поля лендинг перекрывает целиком.

Что чаще всего приходится править после первого запуска:

- Эталон снялся с открытым баннером кук или чатом — добавить их селекторы в `ignoreSelectors`.
- Каждый час приходит уведомление про одно и то же место — посмотреть `data/<slug>/changes/*/change.json`, найти шумящий узел, добавить в `ignoreSelectors` или его текст в `ignorePatterns`.
- Картинки на скриншоте не прогрузились — увеличить `settleMs`.
- Следить нужно только за одним блоком — задать `region`.

## Безопасность

Служба открывает в браузере чужие страницы, содержимое которых не контролирует, и держит при себе токен бота и пароль от почты. Отсюда основные решения:

**Sandbox Chromium включён.** Расхожий совет добавить `--no-sandbox` относится к запуску от root; в нашем образе процесс идёт от `pwuser`, и sandbox поднимается штатно — в том числе с `cap_drop: ALL`. Без него эксплойт рендерера на скомпрометированном лендинге сразу получил бы доступ к `data/` и к переменным окружения с токеном.

**Ограничители на снапшот стоят дважды.** Те, что внутри `page.evaluate`, опираются на прототипы, которыми владеет страница: достаточно переопределить `Array.prototype.push`, и в Node вернётся сколько угодно данных. Поэтому те же рамки ставятся ещё раз в [`clampSnapshot`](src/capture.ts) — там, где страница ни на что не влияет. Заодно чинятся `NaN` в координатах: по ним строятся рамки и режутся фрагменты.

**Секреты** читаются либо из переменной, либо из файла по пути в `<ИМЯ>_FILE`. Второй способ надёжнее: в окружении остаётся путь, а не сам секрет, и токен не виден ни в `docker inspect`, ни в `/proc/1/environ`. Блоки `secrets:` в `docker-compose.yml` закомментированы — раскомментируйте и положите файлы в `secrets/`.

**Токен и пароль вырезаются** из текста любой ошибки перед журналом и `history.jsonl`. Токен лежит в пути URL и всплывает в сообщениях сетевых сбоев; чистка сделана одной точкой в диспетчере уведомлений, чтобы не гадать, какая библиотека что напишет.

**Схемы URL ограничены.** Лендингу разрешены только `http`, `https` и `file` — `z.string().url()` сам по себе пропускает и `javascript:`, и `data:`. Адресу Bot API разрешены только `http` и `https`: токен уезжает в путь запроса, и опечатка в `TELEGRAM_API_BASE` увела бы его не туда.

**Имя лендинга задаёт имя каталога** в `data/`, поэтому `slug` либо генерится с вычисткой всего, кроме `[a-z0-9-]`, либо, если задан руками, проверяется тем же шаблоном.

**Контейнер** работает от непривилегированного пользователя, без единой capability, с `no-new-privileges` и не публикует ни одного порта — входящих соединений у службы нет вовсе. Сети требуется ровно столько, чтобы открыть лендинги и достучаться до SMTP и Bot API; всё остальное, включая npm, при старте не нужно.

Что осталось принятым риском:

- `env_file: .env` кладёт секреты в окружение контейнера — они видны в `docker inspect`. Лечится переходом на `*_FILE`.
- `extraHeaders` из конфига уходят на все запросы, включая редиректы на другой хост. Не кладите туда авторизацию.
- `data/` содержит скриншоты лендингов в открытом виде. Если на них попадают персональные данные, каталог нужно защищать правами файловой системы.

## Ограничения Telegram

У Bot API жёсткие рамки на фото: сумма сторон не больше 10000 пикселей, отношение — не больше 20:1. Полностраничный снимок лендинга (1280 × 12000 и длиннее) в них не влезает, поэтому:

- фрагментами-фото уходят только `focus_N.png` — они по построению ограничены по высоте;
- страница целиком уходит документом (`sendDocument`), там ограничений на габариты нет;
- если фрагмент всё же не проходит по отношению сторон, он пропускается с записью в журнал.

Разметка сообщений — `HTML`, поэтому весь текст, пришедший со страницы, экранируется. Иначе `<b>` в тексте лендинга сломал бы сообщение, а `<a href>` подставил бы в него чужую ссылку.

## Ошибки

Если лендинг не открывается, прогон не падает: лендинг помечается ошибкой в `data/<slug>/history.jsonl`, эталон не трогается. Уведомление уходит только когда неудач подряд накопится `NOTIFY_FAIL_THRESHOLD` (по умолчанию три) — одиночный таймаут не повод будить.

Каналы независимы: упавший Telegram не отменяет письмо и наоборот.

## Раскладка данных

```
data/<slug>/
  baseline/       page.png, snapshot.json, meta.json — текущий эталон
  changes/<ts>/   before.png, after.png, *_marked.png, focus_*.png,
                  pixeldiff.png, change.json
  history.jsonl   по строке на каждый прогон
  state.json      счётчик неудач подряд
```

Хранятся последние 48 отчётов на лендинг, `history.jsonl` обрезается до 10 000 строк. Старое чистится в конце каждого прогона.

## Проверка на фикстуре

В `fixtures/` лежит страница, на которой удобно убедиться, что всё работает: в ней есть баннер кук, блок со случайным числом (проверяет фильтр подтверждения) и текст с угловыми скобками (проверяет экранирование).

```sh
cp fixtures/landing.html /tmp/live.html && cp fixtures/hero-*.svg /tmp/
# добавить в landings.yaml лендинг с url: file:///tmp/live.html
npm run baseline -- --all
npm run check                      # «изменений нет»
# поправить /tmp/live.html — заменить hero-a.svg на hero-b.svg, изменить текст
npm run check                      # изменения найдены, уведомление ушло
```
